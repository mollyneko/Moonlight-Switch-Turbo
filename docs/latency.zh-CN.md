# 延迟推导：1.5.0 → 1.5.16

[README](README.zh-CN.md) 里那张总表背后的逐项推导。三条链路——视频、音频、手柄输入——各自的代码参数依据。


下面所有数字都从代码参数推导，按 **60 fps（一帧 = 16.67 ms）** 计算，且只统计客户端在主机之外额外增加
的那部分。

> 1.5.12 与 1.5.13 只改了主菜单里显示的标题，1.5.14 改的是线程放在哪个核上、而不是压几帧，所以下面的
> 数字描述的就是这个发布版本身。

### 总览

| 链路 | 这个数字约束什么 | 1.5.0 | 1.5.16 | 变化 |
|:---|:---|---:|---:|---:|
| **视频** —— 队列驻留 | 你看到的画面有多旧 | 1.00 帧 · 16.7 ms | 0.00 帧 · **0 ms** | −16.7 ms |
| **输入** —— 采样等待（均值） | 你的按键有多旧 | 0.50 帧 · 8.3 ms | 0.25 帧 · **4.2 ms** | −4.2 ms |
| **视频 + 输入** | 客户端端到端额外增加的量 | 1.50 帧 · **25.0 ms** | 0.25 帧 · **4.2 ms** | **−20.8 ms（−83%）** |
| **音频** —— 播放深度 | 声画偏移 | 5 × 12.5 ms · **62.5 ms** | 2 × 12.5 ms · **25.0 ms** | −37.5 ms |

音频是独立链路：它约束的是声音落后画面多少，而不是画面本身有多旧，所以不计入 25.0 → 4.2 ms 这个总数。

## 三条链路

### 视频链路 —— 解码 → 帧队列 → 后处理 → 呈现

| 改动 | 1.5.0 | 1.5.16 | 效果 |
|:---|:---|:---|:---|
| 队列驻留 | 整个会话固定 `min(深度 − 1, 2)`，默认 1 帧 | 自适应：先取同一个值作为基线，连续流畅 5 秒后降到 **0 帧** | 画面年龄 −16.7 ms |
| 预留恢复 | 每次普通丢失都**重建整个**预留，形成冻结—追赶循环 | 每 5 秒流畅返还一帧；一旦欠载立刻还回去并把等待翻倍（上限 60 秒） | 不再周期性卡顿 |
| 节奏收敛 | 增益 0.01、排空上限 0.08 帧/次绘制 —— 消除积压要 229 次绘制（3.8 秒） | 增益 0.06、上限 0.40 帧/次绘制 —— 37 次绘制（0.62 秒） | 3.8 秒 → 0.6 秒 |
| 追赶上限 | `min(credit, 队列上限)` —— 节奏估计一抖就可能一次丢掉 5–13 帧 | `min(credit, 积压 + 1)` —— 在目标上时积压为 0，就不追赶 | 突发丢帧有界 |
| GPU fence | 发信号后紧接着等待，都在绘制里；CPU 被钉在 GPU 上 | 本帧发信号，**下一帧开头**才等待 —— GPU 干活时跑输入采样和 UI pass | 每帧 1–2 ms 移出输入路径 |
| 后处理 | EASU → RCAS → 拷贝进 framebuffer | 关闭抖动时 EASU → RCAS **直接写 framebuffer** | 1080p 下每帧省约 0.65 ms 带宽 |
| 解码 | `LOW_DELAY` + `FAST` + `SHOW_ALL` + `OUTPUT_CORRUPT`、`FF_THREAD_SLICE` | 完全一致 | 0 |

这七项里只有两项真正改变数字，其余的作用是让流水线不卡住。驻留还取决于帧队列设置，配置越深代价越大：

| 帧队列设置 | 1.5.0 驻留 | 1.5.14 驻留（稳态） |
|:---|---:|---:|
| 1 | 0 ms | 0 ms |
| 2（默认） | 16.7 ms | **0 ms** |
| 3 | 33.3 ms | **16.7 ms** |

硬容量始终是 `深度 + 5` 帧（`kBurstHeadroomFrames`）—— 那是 NVDEC 在突发时避免静默丢 surface 所需的预留。

### 音频链路 —— Opus 解码 → wave buffer → audren

| 改动 | 1.5.0 | 1.5.16 | 效果 |
|:---|:---|:---|:---|
| 池上限 | 5 块 wave buffer，池里有多少就压多少 | **2**（`kMaximumQueuedWaveBuffers`），分配量仍是 5 | 62.5 → 25.0 ms |
| 背压 | 池满时 `write_audio()` 阻塞，于是池永远是满的 | `LiGetPendingAudioDuration() > 30` ms 时整帧丢弃 | 上限从名义值变成实际值 |
| 漂移修正 | 每 400 次调用丢一块 buffer，后面那道 0.5 秒失步保护因为写入被阻塞而永远到不了 | 两者都移除 —— 没有积压可修正了 | 不再周期性爆音 |
| 帧与混音 | 12.5 ms Opus 帧、2 块 mix buffer、24 voice | 完全一致 | 固定成本，不计入 |

丢一帧只是一声爆音；旧行为是整个会话都晚 62.5 ms。

### 输入链路 —— 轮询 → 映射 → 差分 → UDP

| 改动 | 1.5.0 | 1.5.16 | 效果 |
|:---|:---|:---|:---|
| 采样频率 | 每帧 1 次 —— 间隔 16.7 ms | 每帧 **2 次**（仅手柄）—— 间隔 8.3 ms | 平均等待 8.3 → 4.2 ms |
| 采样位置 | 渲染 pass 提交之后，包要等完一整个 pass | 渲染**之前**；第二次采样是呈现前最后一步 | 发送延迟 ≈ 0 |
| 发送策略 | 每个手柄差分，只发变化的状态 | 完全一致 | 0 |
| 触摸、鼠标、键盘 | 帧开始采样 | 相同 —— 第二次采样只覆盖手柄 | 8.3 ms，未变 |
| 逐帧 CPU | `fsqrt_` 位运算开方、每次调用构造 `std::vector`、overlay 再轮询一次手柄、设置按值拷贝 | 平方距离比较、静态缓冲、`rawControllerState()`、`const auto&` | 让第二次采样负担得起 |

4.2 ms 约束的是「按下被检测到」，不是「包已发出」—— 现在发送紧跟采样，只差几微秒而不是一整个渲染 pass。

### 帧时间稳定性 —— 1.5.14

这一版不改上面的任何数字，改的是抖动。

moonlight-common-c 用裸 `pthread_create` 创建它的 13 个工作线程，没有任何平台侧设置，所以在 Switch 上
它们继承不到核掩码、也没有优先级 —— 全部跑在默认的 `0x2C` 上，跟 `main.cpp` 绑在 core 0、优先级 `0x20`
的渲染主循环抢时间片。VideoDec 和 AudioDec 是周期性唤醒、对延迟敏感的负载，被调度到渲染核上，表现出来
就是帧时间抖动和音频爆音，而 CPU 总占用率看着并不高。1.5.14 显式放置它们：

| 线程 | 核心 | 优先级 |
|:---|:---|:---|
| AudioDec | 1 | `0x1E`（比渲染主循环高一档） |
| VideoDec | 2 | `0x20` |
| 渲染主循环（未动） | 0 | `0x20` |

绑核是在解码回调内部完成的 —— `submit_decode_unit` 和 `decode_and_play_sample` 只可能各自跑在自己的线
程上 —— 所以 `moonlight-common-c` 保持未修改的 submodule 状态。放置是幂等的（第一帧付一次 syscall），
从 applet 实际授权的核掩码里解析目标核而不是假定三个核都能用，掩码够不到就静默回退、不影响串流。

**解码线程数**设置在本次构建里被隐藏：硬件解码把解码器固定为单线程，这个选项在 Switch 上不起作用。
桌面构建仍然保留，那里的软解路径会用到它。

预期收益是帧节奏更稳、1% low 更高、音频欠载更少。不要期待平均延迟下降 —— 本文计算的那部分预算不会变。

## 三条链路在同一时间轴上

```
一帧 = 16.7 ms，60 Hz
0                                                                    16.7 ms
|-------------------------------------------------------------------------|
1.5.0
 视频   |---------------- 渲染 + 提交 ----------------|
        |=== 队列：压 1 帧 ===|                      （画面旧 16.7 ms）
 输入                                                       [采样] -> 发送
         ^ 在这里按下，最多要等满一帧

1.5.16
 输入   [采样] -> 发送                                       [采样] -> 发送
 视频   |---------- 渲染 + 提交 ----------|
        | 队列下限：0 帧 |                              （画面旧 0 ms）
         ^ 按下最多只等半帧
```

### 客户端侧合计

| 项 | 1.5.0 | 1.5.16 |
|:---|---:|---:|
| 视频驻留 | 16.7 ms | 0 ms |
| 输入采样等待 | 8.3 ms | 4.2 ms |
| **合计** | **25.0 ms** | **4.2 ms** |

30 fps 时帧周期翻倍，两项都跟着翻倍；120 fps 时减半。Switch 在掌机和底座模式下都是 60 Hz 输出，这也是
客户端向主机宣告的值（`clientRefreshRateX100 = 6000`）。

| 刷新率 | 帧周期 | 1.5.0 | 1.5.16 | 变化 |
|:---|---:|---:|---:|---:|
| 30 fps | 33.3 ms | 50.0 ms | **8.3 ms** | −41.7 ms |
| 60 fps | 16.7 ms | 25.0 ms | **4.2 ms** | −20.8 ms |

## 数字怎么来的

```
T_frame      = 1000 / 刷新率                      -> 60 Hz 时 16.67 ms
T_sample     = T_frame / 每帧采样次数 / 2         -> 按键的平均等待
T_video      = 目标缓冲帧数 × T_frame             -> 显示前压住的帧
T_input      = T_sample
T_client     = T_video + T_input

T_audio      = 最大入队 wave buffer 数 × 12.5 ms  -> 声画偏移，独立链路
```

```
1.5.0    视频  1 × 16.67                   = 16.67
         输入  16.67 / 1 / 2              =  8.33
         合计                               25.00 ms
         音频  5 × 12.5                   = 62.50 ms

1.5.16   视频  0 × 16.67                   =  0.00
         输入  16.67 / 2 / 2              =  4.17
         合计                                4.17 ms
         音频  2 × 12.5                   = 25.00 ms
```

表里的数字保留一位小数；4.2 ms 实为 4.17。

**未计入：** 网络 RTT、主机采集与编码、Switch 侧 FFmpeg 解码、显示扫描输出、音频硬件延迟，以及 audren 的
mix buffer。这些项在两个版本之间相同，所以刻意排除——本文只衡量客户端改动的部分。视频表里 fence 与拷贝
pass 两项标注为估算，因为它们的实际开销取决于 GPU 频率和分辨率。

> [!NOTE]
> 以上是从代码参数推导的理论值，不是实验室实测。真实延迟还取决于链路抖动和主机编码器。
>
> 作为参照：一次 4 ms RTT 的实测会话端到端约 68 ms，其中约 60 ms 是队列积压——正是这条版本线要削掉的
> 部分。那次测量早于节奏修正，所以它是一个上界，而不是当前构建的描述。
