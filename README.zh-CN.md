# Moonlight-Switch-Turbo

[English](README.md) | **简体中文**

面向 Nintendo Switch 的 [Moonlight](https://github.com/moonlight-stream) 串流客户端，fork 自
[XITRIX/Moonlight-Switch](https://github.com/XITRIX/Moonlight-Switch)。

本分支只保留 Switch 一个目标平台，1.5.x 整条版本线都在做同一件事：把客户端这一侧的延迟压掉几帧。具体是
输入在渲染之前发出、手柄每帧采样两次、视频队列自适应降到 0 帧预留、音频池封顶在 25 ms。

---

## 延迟：1.5.0 → 1.5.11

1.5.11 是延迟相关改动全部落地的版本。下面所有数字都从代码参数推导，按 **60 fps（一帧 = 16.67 ms）** 计算，
且只统计客户端在主机之外额外增加的那部分。三条链路——视频、音频、手柄输入——各自拆到子阶段，因为它们的
收益来源和退化方式完全不同。

### 总览

| 链路 | 这个数字约束什么 | 1.5.0 | 1.5.11 | 变化 |
|:---|:---|---:|---:|---:|
| **视频** —— 队列驻留 | 你看到的画面有多旧 | 1.00 帧 · 16.7 ms | 0.00 帧 · **0 ms** | −16.7 ms |
| **输入** —— 采样等待（均值） | 你的按键有多旧 | 0.50 帧 · 8.3 ms | 0.25 帧 · **4.2 ms** | −4.2 ms |
| **视频 + 输入** | 客户端端到端额外增加的量 | 1.50 帧 · **25.0 ms** | 0.25 帧 · **4.2 ms** | **−20.8 ms（−83%）** |
| **音频** —— 播放深度 | 声画偏移 | 5 × 12.5 ms · **62.5 ms** | 2 × 12.5 ms · **25.0 ms** | −37.5 ms |

音频是独立链路：它约束的是声音落后画面多少，而不是画面本身有多旧，所以不计入 25.0 → 4.2 ms 这个总数。

## 1. 视频链路

解码 → 帧队列 → 后处理 → 呈现。这条链上真正改变数字的只有两处，其余改动的作用是让整条流水线不卡住。

### 1.1 队列驻留 —— 16.7 → 0 ms

队列存在的意义是吸收网络抖动。但队列里每压一帧，就是每一帧都多付一帧的延迟，不管这一帧有没有用上。

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| 目标深度 | `min(配置深度 − 1, 2)`，整个会话固定 | 同一个值作为基线，之后自适应 |
| 默认目标（深度 2） | 1 帧 · 16.7 ms | 前 5 秒 1 帧，之后 **0 帧** |
| 下界 | 基线本身 | 深度 ≥ 2 时为 0 帧 |
| 硬容量 | `深度 + 5` 帧（`kBurstHeadroomFrames`） | 相同 |
| 稳态驻留 | 16.7 ms | **0 ms** |
| 欠载后的驻留 | 16.7 ms | 16.7 ms —— 预留会回来 |

配置的队列越深，1.5.0 的固定预留代价越大，所以随设置提高，两者的差距会拉开：

| 帧队列设置 | 1.5.0 目标 | 1.5.11 目标（稳态） | 1.5.0 驻留 | 1.5.11 驻留 |
|:---|---:|---:|---:|---:|
| 1 | 0 | 0 | 0 ms | 0 ms |
| 2（默认） | 1 | 0 | 16.7 ms | **0 ms** |
| 3 | 2 | 1 | 33.3 ms | **16.7 ms** |

### 1.2 节奏收敛 —— 3.8 s → 0.6 s

"配置成浅队列"和"真的坐在浅队列上"是两件事。节奏控制每次绘制都会把播放速率往目标推一点；如果修正力度
不够，一次突发把队列顶深之后，它就一直是深的。

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| 占用率增益 | 每帧 0.01 | **每帧 0.06** |
| 2 帧误差时的修正量 | 0.02 帧/次绘制 | **0.12 帧/次绘制** |
| 最大排空 | 0.08 帧/次绘制 · 4.8 帧/秒 | **0.40 帧/次绘制 · 24 帧/秒** |
| 最大保持 | 0.08 帧/次绘制 | 0.08 帧/次绘制（刻意保持不变） |
| 消除 90% 积压的时间 | `ln(0.1)/ln(0.99)` = 229 次绘制 · **3.8 s** | `ln(0.1)/ln(0.94)` = 37 次绘制 · **0.62 s** |
| 追赶上限 | `min(credit, 队列上限)` —— 节奏估计一抖就可能一次丢掉 5–13 帧 | `min(credit, 积压 + 1)` —— 在目标上时积压为 0，就不追赶 |

这个不对称是故意的。排空太猛会丢掉"本来就已经迟了"的帧，而迟到正是要解决的问题；反过来，为了重建预留而
把一帧多显示一次，是把同一张画面显示两遍，只是卡顿，什么也换不来——所以这个方向保持原来的慢速率。

### 1.3 GPU 提交与 fence 位置

后处理链会跨帧复用渲染目标和 uniform buffer，所以在下一帧覆盖它们之前，必须确认上一帧的链已经跑完。这个
等待放在什么位置，决定了 CPU 会不会被钉在 GPU 上。

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| 发信号 + 等待 | `queueSignalFence()` 之后紧接着 `queueWaitFence()`，都在绘制里 | 本帧发信号，**下一帧绘制开头**才等待 |
| GPU 工作期间 CPU 干什么 | 什么也干不了，被阻塞 | 采样输入、检查 overlay、画上一帧留出的 UI |
| 对输入路径的代价 | 每帧一条后处理链（1080p 下约 1–2 ms） | 0 |

fence 只在延迟等待之后才重新发信号，所以跨帧不会丢信号。

### 1.4 后处理链

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| 阶段 | EASU 放大 → RCAS 锐化 → 拷贝进 framebuffer | 关闭抖动时，EASU → RCAS **直接写 framebuffer** |
| 额外的全分辨率拷贝 | 有，每帧一次 | RCAS-only 路径下没有 |
| 该拷贝在 1080p 的估算代价 | 约 8.3 MB 写 + 8.3 MB 读 ≈ 0.65 ms 显存带宽（按 25.6 GB/s） | 0 |

开抖动时仍然需要中间目标，因为那一趟要读 RCAS 的输出。只有 RCAS 是最后一级时才会省掉拷贝。

### 1.5 启动与欠载恢复

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| 启动 | 填满预留，之后每次普通丢失都**重建整个**预留 | 只在启动时填一次，之后逐帧返还 |
| 恢复节奏 | 冻结—追赶的循环，每一次都是可见的卡顿 | 连续 5 秒不欠载就返还一帧；一旦欠载立刻还回去，并把等待时间翻倍（上限 12 倍，即 60 秒） |
| 挂起后的重同步 | 积压帧一次性倾泻 | 绘制间隔 > 250 ms 就清零信用、跳过倾泻 |

### 1.6 解码 —— 未变

这里专门说明，因为很容易误以为收益来自解码：两个版本的解码器配置完全一致 ——
`AV_CODEC_FLAG_LOW_DELAY`、`AV_CODEC_FLAG2_FAST`、`SHOW_ALL`、`OUTPUT_CORRUPT`，以及按设置线程数的
`FF_THREAD_SLICE`。解码延迟在 1.5.0 和 1.5.11 之间没有变化；变的是它下游的一切。

### 视频小计

| 子阶段 | 1.5.0 | 1.5.11 | 变化 |
|:---|---:|---:|---:|
| 1.1 队列驻留 | 16.7 ms | 0 ms | −16.7 ms |
| 1.2 收敛（瞬态） | 深度偏高最长 3.8 s | 最长 0.6 s | 尾巴缩短 3.2 s |
| 1.3 CPU 侧的 fence 等待 | 每帧 1–2 ms | 0 | 移出关键路径 |
| 1.4 冗余拷贝 | 约 0.65 ms | 0 | −0.65 ms |
| 1.5 启动重建 | 周期性发生 | 只发生一次 | 不再周期性卡顿 |
| 1.6 解码 | 未变 | 未变 | 0 |
| **显示驻留路径** | **16.7 ms** | **0 ms** | **−16.7 ms** |

## 2. 音频链路

Opus 解码 → wave buffer → audren。这条链路不决定画面有多旧，但决定声画同步；而 1.5.0 里它整个会话都钉在
最坏值上。

### 2.1 池深度 —— 62.5 → 25 ms

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| Opus 帧 | 12.5 ms（48 kHz 下 600 个采样） | 相同 |
| 分配的 wave buffer 数 | 5 | 5（未变） |
| 允许入队的 buffer 数 | 5 —— 池里有多少就压多少 | **2**（`kMaximumQueuedWaveBuffers`） |
| 最坏缓冲音频 | 5 × 12.5 = **62.5 ms** | 2 × 12.5 = **25.0 ms** |
| 稳态缓冲音频 | 62.5 ms，因为池一直是满的 | ≤ 25.0 ms |

分配量没动；1.5.11 只是拒绝往第三块 buffer 里压。

### 2.2 背压策略 —— 阻塞 → 丢弃

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| 池满时 | `write_audio()` 阻塞，直到有 wave buffer 空出来 | `LiGetPendingAudioDuration() > 30` ms 时整帧丢弃 |
| 对池的影响 | 永远是满的 —— 后面那道 0.5 s 失步保护根本执行不到 | 稳定在 2 块以内 |
| 后果 | 整个会话音频都晚 62.5 ms | 音频最多晚 25 ms；丢一帧是一声爆音，而不是持续累积的滞后 |

这是让"池深度"从名义值变成实际值的那个改动。

### 2.3 漂移修正 —— 已移除

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| 机制 | 每 400 次调用丢一块 buffer | 已移除 |
| 0.5 s 失步保护 | 代码里有，但写入先被阻塞，永远到不了 | 已移除 |
| 原因 | 它在补偿一个现在被上限阻止了的积压 | — |

### 2.4 帧与混音缓冲

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| Opus 帧 | 12.5 ms | 12.5 ms |
| audren mix buffer | 2 | 2 |
| voice 数 | 24 | 24 |

这些都是固定成本，不计入差值。

### 音频小计

| 子阶段 | 1.5.0 | 1.5.11 | 变化 |
|:---|---:|---:|---:|
| 2.1 队列深度 | 62.5 ms | 25.0 ms | −37.5 ms |
| 2.2 背压 | 钉在上限 | 有界，溢出即丢 | 保证 2.1 不反弹 |
| 2.3 漂移修正 | 周期性丢帧 | 不再需要 | 每 400 帧少一次爆音 |
| 2.4 帧 / 混音 | 12.5 ms / 2 块 | 未变 | 0 |
| **播放深度** | **62.5 ms** | **25.0 ms** | **−37.5 ms（−60%）** |

## 3. 手柄输入链路

轮询 → 映射 → 差分 → UDP。下面就是整条路径的子阶段。1.5.x 改了第一段和第三段，并且把每帧的 CPU 开销削到
了让"每帧采样两次"变得便宜的程度。

### 3.1 采样频率 —— 1 次/帧 → 2 次/帧

按键可能落在采样间隔里的任意位置。采样均匀时，期望等待是间隔的一半。

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| 每帧采样次数 | 1 | **2** |
| 采样间隔 | 16.7 ms | **8.3 ms** |
| 按键的平均等待 | 8.3 ms | **4.2 ms** |
| 最坏等待 | 16.7 ms | **8.3 ms** |

第二次采样只覆盖手柄。键盘差值和底栏计时仍留在帧开始那一次调用上，行为未变。

### 3.2 采样在帧内的位置

频率不是全部——采样得早、发得晚，一样是晚。

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| （唯一/第一次）采样在哪 | 渲染提交之后 | 渲染**之前** |
| 包发出前多等的时长 | 一个渲染 pass 的时长 | 0 |
| 第二次采样位置 | — | 绘制回调的最后一步，紧贴呈现 |

所以 4.2 ms 是"按下被检测到"的数字，不是"包已发出"的数字。现在发送紧跟采样，只差几微秒，而不是差一整个
渲染 pass。

### 3.3 发送策略 —— 差分，未变

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| 比较方式 | 每个手柄 `GamepadState::is_equal` | 相同 |
| 发送内容 | 只发变化了的状态 | 只发变化了的状态 |
| 空闲时开销 | 每次采样每手柄一次比较 | 两次比较 —— 依然可忽略 |

差分意味着按键会在"第一个观测到它的采样点"发出，正好等于上面的采样等待。也意味着按住不放时，两个版本都不
额外占带宽。

### 3.4 触摸、鼠标、键盘子路径

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| 采样时机 | 帧开始 | 帧开始 |
| 是否被第二次采样覆盖 | — | 否 |
| 平均等待 | 8.3 ms | 8.3 ms（未变） |

触摸和鼠标没有变快，本文也不声称它们变快了。双采样只加在便宜且安全的地方：手柄。

### 3.5 去掉的逐帧 CPU 开销

| | 1.5.0 | 1.5.11 |
|:---|:---|:---|
| 摇杆死区 | `fsqrt_` 位运算开方，再比较 | 平方距离比较 —— 精确且不用开方 |
| 触摸状态缓冲 | 每次调用构造 `std::vector` | 静态缓冲，清空复用 |
| 手柄快照 | overlay 组合键检查再轮询一次 | 通过 `rawControllerState()` 复用 |
| 设置拷贝 | `auto guideKeys`，每次调用拷贝一份 | `const auto&` |

单独看都是亚毫秒级；合起来才是"每帧多采一次"能负担得起、而不是把输入路径成本翻倍的原因。

### 输入小计

| 子阶段 | 1.5.0 | 1.5.11 | 变化 |
|:---|---:|---:|---:|
| 3.1 采样等待（均值） | 8.3 ms | 4.2 ms | −4.2 ms |
| 3.1 采样等待（最坏） | 16.7 ms | 8.3 ms | −8.3 ms |
| 3.2 发送偏移 | 一个渲染 pass | ~0 | −1 个渲染 pass |
| 3.3 差分 / 发送 | 变化时发送 | 变化时发送 | 0 |
| 3.4 触摸 / 鼠标 | 8.3 ms | 8.3 ms | 0 |
| 3.5 逐帧 CPU | 开方 + 分配 | 比较 + 复用 | 亚毫秒 |
| **按下到发包（均值）** | **8.3 ms** | **4.2 ms** | **−4.2 ms（−50%）** |

## 4. 三条链路在同一时间轴上

```
一帧 = 16.7 ms，60 Hz
0                                                                    16.7 ms
|-------------------------------------------------------------------------|
1.5.0
 视频   |---------------- 渲染 + 提交 ----------------|
        |=== 队列：压 1 帧 ===|                      （画面旧 16.7 ms）
 输入                                                       [采样] -> 发送
         ^ 在这里按下，最多要等满一帧

1.5.11
 输入   [采样] -> 发送                                       [采样] -> 发送
 视频   |---------- 渲染 + 提交 ----------|
        | 队列下限：0 帧 |                              （画面旧 0 ms）
         ^ 按下最多只等半帧
```

### 客户端侧合计

| 项 | 1.5.0 | 1.5.11 |
|:---|---:|---:|
| 视频驻留 | 16.7 ms | 0 ms |
| 输入采样等待 | 8.3 ms | 4.2 ms |
| **合计** | **25.0 ms** | **4.2 ms** |

30 fps 时帧周期翻倍，两项都跟着翻倍；120 fps 时减半。Switch 在掌机和底座模式下都是 60 Hz 输出，这也是
客户端向主机宣告的值（`clientRefreshRateX100 = 6000`）。

| 刷新率 | 帧周期 | 1.5.0 | 1.5.11 | 变化 |
|:---|---:|---:|---:|---:|
| 30 fps | 33.3 ms | 50.0 ms | **8.3 ms** | −41.7 ms |
| 60 fps | 16.7 ms | 25.0 ms | **4.2 ms** | −20.8 ms |

## 5. 数字怎么来的

```
T_frame      = 1000 / 刷新率                      -> 60 Hz 时 16.67 ms
T_sample     = T_frame / 每帧采样次数 / 2         -> 按键的平均等待
T_video      = 目标缓冲帧数 × T_frame             -> 显示前压住的帧
T_input      = T_sample
T_client     = T_video + T_input

T_audio      = 最大入队 wave buffer 数 × 12.5 ms  -> 声画偏移，独立链路
```

```
1.5.0    视频  1 × 16.67                   = 16.67
         输入  16.67 / 1 / 2              =  8.33
         合计                               25.00 ms
         音频  5 × 12.5                   = 62.50 ms

1.5.11   视频  0 × 16.67                   =  0.00
         输入  16.67 / 2 / 2              =  4.17
         合计                                4.17 ms
         音频  2 × 12.5                   = 25.00 ms
```

表里的数字保留一位小数；4.2 ms 实为 4.17。

**未计入：** 网络 RTT、主机采集与编码、Switch 侧 FFmpeg 解码、显示扫描输出、音频硬件延迟，以及 audren 的
mix buffer。这些项在两个版本之间相同，所以刻意排除——本文只衡量客户端改动的部分。§1.3 和 §1.4 里的
fence 与拷贝 pass 标注为估算，因为它们的实际开销取决于 GPU 频率和分辨率。

> [!NOTE]
> 以上是从代码参数推导的理论值，不是实验室实测。真实延迟还取决于链路抖动和主机编码器。
>
> 作为参照：一次 4 ms RTT 的实测会话端到端约 68 ms，其中约 60 ms 是队列积压——正是 1.5.11 要削掉的部分。
> 那次测量早于节奏修正，所以它是一个上界，而不是当前构建的描述。

## 安装

1. 从 [Releases](https://github.com/mollyneko/Moonlight-Switch-Turbo/releases) 下载最新的
   `Moonlight-Switch-Turbo-*.zip`
2. 把 `Moonlight-Switch.nro` 解压到 `sdcard:/switch/Moonlight-Switch/`
3. 通过 **Title Redirection** 启动 hbmenu（需要完整内存权限）
4. 启动 Moonlight-Turbo

> [!IMPORTANT]
> 主菜单标题是 `Moonlight-Turbo`，但数据目录仍然是 `switch/Moonlight-Switch/`。你的设置和收藏都在那里，
> 不受改名影响。

> [!TIP]

## 操作

**鼠标** —— 触摸屏移动光标，轻点左键，双指滚动。触摸期间 ZL/ZR 充当左右键，左右摇杆充当滚轮。USB 鼠标
也可用。

**键盘** —— 三指轻点屏幕呼出软键盘；USB 键盘可直接使用。

**手柄** —— 默认映射为 X360 手柄（A/B 与 X/Y 互换），可在设置里重新映射。最多 5 个控制器（含掌机模式），
支持单只 Joy-Con。

**六轴** —— 在 Sunshine 里把手柄识别为 DS4 即可获得陀螺仪与加速度计。仅限玩家 1。

**游戏内覆盖层** —— 默认同时按 `-` 和 `+`，或按住键盘 `ESC`。组合键和按住时长都可配置。

**NSP 前向器** —— 带预设参数直接开始串流。先把目标应用加入收藏，再用
[NSP Forwarder Generator](https://nsp-forwarder.vercel.app/moonlight) 生成。手动方式传
`--ip` / `--appid` / `--appname`，例如 `--ip=192.168.1.101 --appid=1233211234 --appname=Steam`。

## 构建

需要 devkitPro 的 devkitA64、libnx 与 Switch portlibs，以及 CMake 3.13+ 和 Ninja。

```bash
git clone --recursive https://github.com/mollyneko/Moonlight-Switch-Turbo
cd Moonlight-Switch-Turbo
cmake -B build/switch -DCMAKE_BUILD_TYPE=Release -DPLATFORM_SWITCH=ON -DUSE_DEKO3D=ON -G Ninja
ninja -C build/switch Moonlight.nro
```

产物在 `build/switch/Moonlight.nro`。`-DUSE_DEKO3D=ON` 选择 deko3d 后端，这是低延迟路径的前提。

如果 `uam`（deko3d 着色器编译器）不可用，构建会从 `resources/shaders/` 复制预编译好的 `.dksh`，而不是在
配置阶段直接报错。

## 已知限制

- 只构建 Switch；Android、iOS、PSV 和桌面端已移除
- 链路持续抖动时，自适应队列会退回 1 帧预留 —— 延迟回到 1.5.0 的水平，换取不卡顿
- 配置的队列越深，自适应下界越高（设置为 3 时稳态是 1 帧，不是 0）
- 触摸和鼠标没有享受双采样，平均等待仍是 8.3 ms
- 六轴需要主机把手柄识别为 DS4；Switch Pro 手柄的陀螺仪轴不会原生透传
